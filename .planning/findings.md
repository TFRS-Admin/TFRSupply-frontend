## 0. Skill-availability discrepancy (flag per instructions)

`AGENTS.md` and `CLAUDE.md` both assert this repo's process is governed by account-wide skills named `agent-skills:*` (e.g. `agent-skills:using-agent-skills`, `agent-skills:spec-driven-development`, `agent-skills:code-review-and-quality`) and `mattpocock-skills:*` (e.g. `mattpocock-skills:tdd`, `mattpocock-skills:code-review`). **At the time this audit's research phase ran, none of these skill names appeared in the session's loaded skill list.** I flagged that plainly rather than silently proceeding as if `agent-skills:using-agent-skills` existed, and worked from built-in equivalents (`code-review`, `simplify`) instead.

**Update, same day:** the marketplaces backing both plugin sets (`mattpocock/skills` and `addyosmani/agent-skills` on GitHub) were registered and enabled via a settings script, and both `agent-skills:*` and `mattpocock-skills:*` now load in-session. That closes the immediate gap, but opens a governance question worth a maintainer decision rather than silent adoption: `~/.claude/settings.json`'s `extraKnownMarketplaces` entries for both point at unpinned branches on two individuals' personal GitHub accounts (not an org-owned or version-pinned source), and this is a user-level (not repo-level) settings file, so it isn't itself visible to `git log` in this repository — nobody reviewing this repo's history would see that its documented process now depends on live, third-party, unpinned plugin code. Recommend: (a) pin both marketplaces to a specific tag/commit rather than tracking a branch, and (b) record the dependency (source, version pinned, date enabled) somewhere in this repo — `AGENTS.md` already references these skills by name but never states where they come from or that they're external, individually-maintained repos rather than an Anthropic- or org-controlled set.

## 5. Business continuity / system of record

- **No database exists for this app.** Confirmed by repo-wide grep and by `ARCHITECTURE.md`'s own (verified-true) claim: Shopify is the system of record for commerce data (catalog, cart, checkout) via the Storefront API, gated by `VITE_SHOPIFY_STOREFRONT_ENABLED`; when unset, the app falls back to committed static JSON in `src/data/`.
- **Admin surfaces are demo/mock-only** (`docs/architecture/ADMIN_AUTHENTICATION_WORKSPACE.md`, confirmed by reading the doc): `/admin/*` auth is a frontend-only, in-memory mock with four fixed demo identities, no real backend, no persisted sessions past a page reload's adapter instance. `.env.example` itself documents `VITE_ADMIN_ENABLED` as "a deployment-level compensating control, not real server-side enforcement" (referencing issue #297) — i.e., the repo's own comments already flag that admin routes are not really secured, only hidden from the build when the flag is unset.
- **Quote requests are not persisted by this app at all.** `VITE_QUOTE_DELIVERY_ENDPOINT` (optional) POSTs quote requests to a third-party hosted form service (Formspree/Basin-shaped, not named/pinned to a specific vendor in the repo); if unset, quotes fall back to a `mailto:` link. Whatever third-party endpoint is actually configured in Railway's env vars (not visible from this session) is a real, undocumented-in-architecture data holder for customer quote requests — it should be named explicitly (which vendor, which account) in a docs PR, since today the repo only describes it generically.
- Net conclusion: **this app has nothing resembling a database to back up.** The actual DR-relevant assets are (a) the Git history itself (GitHub-hosted, needs branch protection + no force-push as its real "backup"), (b) Shopify's own store configuration/catalog (external system, needs its own export/backup plan outside this repo), and (c) whatever third-party quote-delivery form service is actually wired up in Railway (needs to be named and its own export capability checked).
